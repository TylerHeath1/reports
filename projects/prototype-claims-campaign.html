How this merges into the codebase

Everything on the other three screens maps to the changes below — 1 new table, 1 new column, 0 new API endpoints. Nothing about moderation or existing claims changes.

⚠ Compliance note: the brand dashboard displays only data that is already public — claim status comes from the same public search API anyone can query. No new data access is granted to brands, which removes the SOC-2 access question the earlier design carried. Internal campaign attribution (campaign_id) is visible to OS Hub staff only. Standard feature review still applies.

What this does NOT touch

  • Moderation permissions — /api/facility-claims/ stays superuser-only (the team view only adds an optional campaign filter to it)
  • Claim review, approve / deny / revoke logic
  • Promotion logic on production location pages
  • Existing claims — campaign_id is null for all of them
  • The v1 / OpenSearch API code — the dashboard calls it, we don't extend it
  • Claim form steps 2–4 (Contact, Business, Profile)
Why this is a point-one: campaigns are a label + a lens. The label: one nullable column and a code. The lens: two existing APIs read side by side — roster from legacy, status from v1. All the hard machinery — the claim form, verification, moderation, automation — already exists and is reused as-is. It also closes the gap the Asda experiment exposed: brands could only track their campaign by being handed the whole admin queue.

Known v1 trade-offs (upgrades with evidence, not up front): statuses refresh with the search index (minutes, not instant) — a dedicated real-time endpoint is the v2 upgrade if a customer demands it; the public field doesn't distinguish "denied" (shows as unclaimed to the brand — your team still sees it in the moderation view); campaign links use the guessable campaign code instead of secret tokens (harmless — every claim is verified before approval).
