Processing Type search: flat index, hierarchy as context

The taxonomy is a display model, not a search model. Every value that exists in the data — the ~130 apparel taxonomy terms and the free-text values contributors have uploaded — lives in one flat, searchable index. The parent shows up as a breadcrumb on the result row, never as a gate in front of it. Values with no parent simply don't render a breadcrumb, and stay perfectly findable.

What to look at

1
One index, two groups. Results split by match source — “Standard types” vs “Contributor values” — not by taxonomy. Honest about what we know, and requires inventing no new ontology.
2
Badge, not bucket. Unmapped values carry a Not in taxonomy badge. An “Other” category would make a false claim about where the value belongs, become your largest node, and churn with every new sector.
3
Counts answer the real question. “Is this a match for your data set?” is a volume question. 4,210 facilities and 3 facilities are both “matches” — the user needs to tell them apart before committing.
4
Index the data, not the schema. Only values with at least one facility appear. If nobody ever uploaded it, it never autocompletes.
5
Multi-parent works for free. Embroidery, Embellishment and Pressing already sit under two facility types 2 parents. A flat index shows both; a cascade has to pick one and hide the other.
6
Upward inference, not downward restriction. Choosing a processing type fills in its parent(s). Choosing a facility type only ranks — it never removes a value that exists.
7
The empty state is the teaching moment. Search “garment washing” or “xylophone” — nearest neighbours with counts do more to convey the shape of the data than any help text.

Why not gate on sector first

Both sector-gate options relocate the problem instead of solving it, and charge every user a step to do it.

01

The gate needs the answer it's meant to produce

To route “kombucha brewing” into a non-apparel branch you must already know its sector — the same classification work as assigning it a parent. The unmapped pile is unmapped precisely because nobody has classified it. A gate moves the pile up one level.

02

A cost on every single search

Users often don't know the sector. Facilities genuinely span sectors — a mill dyeing both apparel fabric and upholstery. And a required first step in front of the thing people came to do is the classic place searches get abandoned.

03

Sector is a great facet, a bad gate

Same information, applied after results instead of before: multi-select, removable, reversible, and derivable from facility records you already hold. You keep the scoping benefit and drop the dead end.

The side effect: parentless values become a ranked work queue

Sort unmapped values by facility count and by how often people search for them, and the “problem” turns into a prioritised backlog for growing the taxonomy. These stop being a permanent class and start being a queue — which fits the all-sectors direction far better than freezing them into an “Other” node. (Counts below are illustrative placeholders.)

Today vs. proposed

Today
  • Exact match only — a value must be typed perfectly to be found.
  • Facility type removes processing type options, hiding values that exist.
  • Contributor values with no parent are effectively invisible in search.
  • No signal about whether a term returns 4,000 facilities or 3.
  • Values under two parents have to pick a side.
  • Zero results is a dead end with no next move.
Proposed
  • Prefix-of-any-word type-ahead over one flat index of every value in the data.
  • Facility type ranks; processing type infers its parent upward.
  • Unmapped values are first-class results, badged rather than bucketed.
  • Facility count on every suggestion; zero-count values never appear.
  • Multi-parent values show all their breadcrumbs.
  • Empty state offers nearest neighbours with counts.
